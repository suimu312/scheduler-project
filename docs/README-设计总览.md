# README‑设计总览.md

> 文件路径：`docs/README‑设计总览.md` 多智能体需求生成工作流系统｜项目总览文档，作为整套设计文档入口，汇总整体目标、工作流、角色、关键机制、模块分工与文档索引。

## 1 项目概述

### 1.1 解决问题

用户仅提供一句模糊业务想法，想要产出一份可确认、可签字的正式需求规格，现实中存在几个痛点：

1. 用户只能表达自己想到的内容，无法完整暴露隐性假设；
2. 提问者不熟悉专业领域，提不出关键问题；
3. 立场冲突需要多方博弈，但实际会议很难凑齐全部利益相关方，也缺少专门扮演反对、质疑视角的参与者。

本系统将不同利益相关方建模为角色智能体，**让智能体先完成立场博弈、冲突辩论，人类只负责审阅结论与做出最终取舍**。

### 1.2 核心价值

1. 将需求背后的隐性假设显性化；
2. 把分歧与冲突暴露在编码开始之前；
3. 全流程过程留痕，每一条需求具备完整来源追溯。

### 1.3 系统边界（不做什么）

- ❌ 不做自动代码生成；
- ❌ 不做需求正确性数学证明；
- ❌ 不追求完全无人值守全自动运行。

**人与机器分工：**

- 人：输入原始想法、做最终取舍确认、签署需求基线；
- 机器：识别分歧、组织多轮讨论、生成多套方案、产出结构化需求材料，把全部选项和冲突摆出来交给人。

## 2 整体工作流：七阶段与两道闸门

系统完整流程分为7个阶段，编排调度器基于状态机+闸门判定，控制阶段流转。

| 阶段              | 主导方       | 主要行为                                              | 阶段产出物                       |
| ----------------- | ------------ | ----------------------------------------------------- | -------------------------------- |
| P1 想法输入       | 人           | 输入自然语言原始想法，无需结构化                      | 原始想法文本                     |
| P2 问题识别与召集 | 智能体编排层 | 将想法拆解为功能/技术/成本/风险四类问题，确定参与角色 | 问题清单 + 角色召集表            |
| P3 多体讨论       | 协商族Agent  | 动态角色召集，执行三段式发言，识别登记冲突            | 讨论纪要 + 冲突登记表            |
| P4 多方案生成     | 智能体       | 并行产出成本优先、体验优先、扩展优先三套方案          | 三套方案文档 + 方案比选表        |
| P5 对抗式评审     | 协商族Agent  | 支持方、质疑方交叉对抗评审，多维度打分                | 评分表 + 评审问题清单            |
| P6 需求生成       | 加工族Agent  | 融合方案比选结果，输出条目化需求规格                  | 需求规格文档 + 冲突‑需求覆盖矩阵 |
| P7 人工确认       | 人           | 审阅、修改、确认签署                                  | 正式需求基线v1.0 + 确认单        |

> 和课堂六阶段映射：将“多体讨论”拆分为P2问题召集 + P3多体讨论；“建设方案”改为并行三套方案生成；“多方评价”细化为带举证约束的对抗评审；需求生成和人工确认拆为P6、P7。

### 阶段流转判定（闸门规则）

全部流转条件由调度器代码判定，仅P7基线签署由人完成。

| 阶段转移      | 判定条件                                          | 判定主体 |
| ------------- | ------------------------------------------------- | -------- |
| P2 → P3       | 每个问题完成类型识别、置信度打分、绑定责任角色    | 代码     |
| P3 → P4       | 冲突清单无未决冲突，或迭代轮次到达上限3轮         | 代码     |
| P4 → P5       | 三套方案基于同一套功能清单与约束生成完成          | 代码     |
| P5 → P6       | 加权总分≥80、无否决项、维度分标准差＜12           | 代码     |
| P5 → 人工介入 | 修改迭代达到3次，或者LLM调用预算耗尽              | 代码     |
| P6 → P7       | 覆盖矩阵无空行，所有冲突/评审问题均被需求条目覆盖 | 代码     |
| P7 → 冻结基线 | 人工审阅确认签署                                  | 人       |

## 3 Agent角色模型：协商族 & 加工族

共6个智能体，分为两类：**协商族具备立场，参与辩论博弈；加工族无立场，仅负责整理输出，不参与争论**。

| 编号 | 角色       | 核心职责                                         | 否决权限                   |
| ---- | ---------- | ------------------------------------------------ | -------------------------- |
| A1   | 产品经理   | 理解原始想法，界定业务范围、优先级，主导方案撰写 | 无                         |
| A2   | 用户代表   | 输出业务功能、使用场景、用户痛点                 | 核心场景不可行时拥有否决权 |
| A3   | 技术架构师 | 技术选型、架构设计、可行性评估                   | 技术完全不可行拥有否决权   |
| A4   | 质量评审员 | 评估风险、完整性、成本、安全隐患                 | 存在阻断级缺陷拥有否决权   |
| A5   | 需求分析师 | 整理功能/非功能需求、优先级、验收标准            | 无                         |
| A6   | 需求确认员 | 核查一致性，识别遗漏、冲突问题                   | 无                         |

> 重要约束：产品经理不再承担会议主持工作；编排调度器统一负责流程调度、角色上场控制，避免“既当球员又当裁判”。

### 各阶段上场角色

| P3多体讨论 | 上场：A1/A2/A3/A4；不上场：A5/A6 | 加工族无立场，入场只会稀释讨论信息密度 |
| ---------- | -------------------------------- | -------------------------------------- |
| P5对抗评审 | 上场：A2/A3/A4/A5；不上场：A1    | 方案作者回避评审自身产出内容           |

### 保证Agent异质性三要素

1. **立场**：每个角色预设自身利益关注点；
2. **知识边界**：做上下文切片，不同Agent拿到不同子集信息，避免全知角色；
3. **否决权**：定义不同角色意见的权重与阻断条件。

## 4 核心机制简述

### 4.1 P3多体讨论：分类召集 + 三段式发言

1. **先分类，再召集** 将原始想法拆分为功能、技术、成本、风险四类；支持多标签；设置置信度阈值，置信不足直接召集全员；绑定每类问题的必到场角色，防止分类出错漏掉关键角色。
2. 三段式发言，禁止自由闲聊式轮流发言
   - 并行陈述：多Agent同时输出，互不可见；输出固定三部分：我要什么、我担心什么、我质询对象；
   - 定向质询：一对一问答，必须引用对方原话，跨立场优先配对；
   - 结构化表态：针对冲突清单逐条投票（接受 / 有条件接受 / 反对），限制理由字数。
3. **冲突识别**：统一议题词表，同一议题出现多种立场自动登记冲突表。
4. **举手补充机制**：允许临时补充观点，但必须标注性质，绑定到已有发言，限制字数与次数，禁止抛出全新独立观点。
5. **冲突三级裁决** ①证据优先，有材料数据一方占优；②无明确证据按权重投票（A2、A4权重1.5，其余1.0）；③仍然平局则挂起，交给人类决策。
6. **终止与防退化约束**：冲突全部解决 / 满3轮迭代 / 调用预算耗尽 / 人工中止即停止；相似度过高发言判定无效；角色长期未被点名强制给予发言机会。

### 4.2 P4‑P5 多方案生成与对抗评审

1. **三套方案不是三个独立答案**：成本优先、体验优先、扩展优先三套方案，必须基于同一套功能清单、同一套约束，差异仅体现在取舍权衡。输出比选表，**按功能项做融合选取，而不是整体三选一**。

2. **对抗评审举证强制约束**：每一条质疑必须写明：问题描述、影响需求条目、严重等级、不改的具体后果；无后果描述不算有效质疑；设置驳回率，防止无意义挑刺。

3. **打分规则**

   | 维度       | 打分角色                   | 权重 |
   | ---------- | -------------------------- | ---- |
   | 功能完整性 | 用户代表A2                 | 25   |
   | 技术可行性 | 架构师A3                   | 25   |
   | 风险与安全 | 质量评审A4                 | 25   |
   | 可测试性   | 需求分析师A5               | 15   |
   | 成本合理性 | 产品经理A1（仅估算不计分） | 10   |

4. 回炉策略：方案层面问题退回架构重设计；需求根源矛盾直接退回P3局部质询；设置全局总LLM调用上限30次防止死循环。

### 4.3 P6‑P7需求生成与基线管理

1. 需求条目格式

   ：编号、标题、描述、Given‑When‑Then验收标准、MoSCoW优先级、依赖关系、来源追溯。

   > 硬性校验：缺失验收标准，不允许流转到人工确认阶段。

2. **覆盖矩阵做遗漏检查**：冲突、评审问题作为行，需求条目作为列；空行即代表需求遗漏，覆盖率可量化计算，不靠人工口头检查。

3. 人工确认支持三种动作：通过、打回（写明约束条件回退P3）、批注修改；同一原始想法最多打回2次。

4. 基线冻结：P7确认完成得到基线v1.0；后续变更走变更请求流程：提交变更、影响分析、重走评审、发布新版本基线。

## 5 技术方案选型

- 编排方案：**自研轻量编排，状态机 + YAML配置驱动流程**
- 不采用AutoGen GroupChat：该库把角色发言顺序交给模型，本系统需要精确控制上场角色、对话模式、质询配对，不适合交由大模型自主调度。
