# 多智能体任务分解与编排系统 · 设计总览

> 本文件是整套设计文档的入口与索引，内容与《第10组-多智能体任务分解与编排系统设计方案（修订版V2）》一致。
> 数据契约以 `docs/architecture.md` 开头为准，本文只做汇总，不另立字段。

## 1 系统定位与作业对应

### 1.1 一句话定位

输入一份设计规格（design spec），由产品经理智能体把它拆成可执行的开发任务，编排器（代码）把这些任务按依赖关系排出施工顺序——先做哪一波、哪些可以并行、哪条链路决定总工期，最后把这套顺序和执行过程以图形化方式呈现。

本系统服务的是"从设计规格到开发任务分解、编排及可视化"这一段流程，是完整软件开发流程中的一段，不是全流程。系统本身做成通用可定制的 SE 工作流：换一份设计规格（"我要做微信"或"我要做小红书"），同一套引擎就能重新跑出另一份任务清单与排期。

### 1.2 作业要求与本方案的对应

| 作业要求 | 对应章节 | 交付物 |
| --- | --- | --- |
| 设计规格输入 | 1.2、P1 阶段 | `design_spec.json`（规范化后的设计规格） |
| PM Agent 做开发任务分解 | 3.6（P6）、4.4、5.1 | `dev_task_list.json`（WBS：任务、依赖、工时、负责人、验收） |
| 编排器生成任务编排 | 3.7（P7）、5.2 排期算法 | `schedule.json`（波次、关键路径、并行度、工期） |
| 可视化 | 6.2–6.7 | `runs/<run_id>/viz/index.html`（泳道甘特、依赖图、时间轴） |

### 1.3 输入契约：设计规格字段

输入只有一份：人提供的设计规格。可以是 Markdown、Word 或 JSON，进入引擎前必须规范化成下表字段，缺字段由 P1 退回或标为假设，不允许模型猜测补齐。

| 字段 | 含义 | 必填 | 示例 |
| --- | --- | --- | --- |
| `spec_id` | 规格标识 | 是 | SPEC-001 |
| `product` | 产品名与一句话目标 | 是 | 校园二手交易平台：让学生在校内完成二手交易 |
| `scope_in` | 本期做，逐条可判定 | 是 | 发布商品、站内消息、搜索筛选 |
| `scope_out` | 本期不做，写明排除理由 | 是 | 不做支付、不做物流 |
| `features` | 功能点清单（FEA-*） | 是 | FEA-001 发布商品 |
| `constraints` | 技术、合规、成本约束（CON-*） | 是 | 必须复用学校统一身份认证 |
| `modules` | 模块划分与职责（MOD-*） | 是 | MOD-001 商品服务 |
| `nfr` | 非功能指标（可测） | 否 | 搜索 p95 ≤ 300ms |
| `acceptance_policy` | 验收口径写法约定 | 否 | Given-When-Then |

输出分四类，全部落在 `runs/<run_id>/`：开发任务清单（WBS）、排期表、人工确认单与基线版本、可视化页面。四类产物都带 `meta`（schema_version、run_id、stage、produced_by、created_at），缺 meta 拒收；任务清单每条任务必须同时带来源引用与验收口径，否则不进 WBS。

### 1.4 四条不做边界

1. **不生成代码与用例正文**：本段终点是"可执行的任务与顺序"，代码生成属于下一段。
2. **不替代人做范围决策**：砍功能、延期、合并里程碑必须由人批准，系统只给建议与代价。
3. **不做跨项目工时校准**：工时是经验估算，必须标注依据（历史卡、类比模块或人给定的基准）。
4. **不承诺适配所有技术栈**：先在一个案例上做透，换栈时替换 `constraints` 与 `modules` 即可复用引擎。

### 1.5 三条设计原则

- **控制权在代码，不在模型**："下一步做什么"永远由状态机判定，不是模型的语言输出——这也是不套用对话式编排框架的根本理由。
- **一切皆事件**：所有动作先追加进 `events.jsonl`，界面与回放都是事件的投影；事件流是唯一事实来源，崩溃后可按事件与状态快照复现到每一步。
- **可计算的才算条件**：闸门、终止、裁决、排期全部写成返回布尔值或数值的纯函数；纯函数不调模型，判定不耗预算。

## 2 数据模型与接口契约

### 2.1 六条交换原则

1. 运行时产物一律 JSON（UTF-8、snake_case），落在 `runs/<run_id>/artifacts/`。
2. 配置一律 YAML，只存在于 `flow.yaml`、`gate_rule.yaml`、`agent_config.yaml`。
3. 模块间禁止互相引用内部结构，只能通过 `StageContext` 与 `StageResult` 信封传递。
4. 每个产物必须带 `meta`，缺 meta 拒收；公共字段名与类型由本文锁定，私有数据放 `extensions`。
5. 枚举集中定义，代码中禁止魔法字符串。
6. 引用统一写成 `source_ref`，格式"产物名:ID"（如 `dev_task_list:DEV-003`），禁止裸 ID，禁止自由文本描述来源。

### 2.2 唯一状态枚举

| 枚举 | 取值 |
| --- | --- |
| StageId | P1 P2 P3 P4 P5 P6 P7 |
| RunStatus | running waiting_human frozen escalated aborted |
| AgentId | A1 产品经理、A2 用户代表、A3 架构师、A4 质量评审员、A5 需求分析师、A6 需求确认员 |
| AgentFamily | deliberative（A1–A4，有立场）、processing（A5–A6，无立场） |
| TaskStatus | pending ready running done blocked |
| Priority | M（Must）S（Should）C（Could）W（Wont） |
| ConflictLevel | L1_evidence L2_weighted_vote L3_escalate |

### 2.3 ID 规范与追溯链

| 对象 | 格式 | 产生者 | 追溯上游 |
| --- | --- | --- | --- |
| 设计规格 | SPEC-001 | 人（P1 规范化） | 原始文档 |
| 功能点 | FEA-001 | 编排器（P2） | SPEC |
| 模块 | MOD-001 | A1 产品经理（P2） | FEA |
| 开发任务 | DEV-001 | A1 产品经理（P6） | FEA / CON / MOD |
| 波次 | WAVE-01 | 编排器（P7 排期） | DEV 依赖 |
| 冲突 | CFL-001 | D（P3） | agent.statement |
| 质疑 | CHG-001 | D（P5） | FEA / DEV |
| 基线 | baseline v1.0 | F（P7） | 确认单 + 全部产物 |

功能点是贯穿全流程的主线：P2 拆出功能点，P4 三套方案引用同一批功能点，P6 把功能点落成任务卡，P7 按任务卡排期。方案生成阶段只能引用功能点，不能引用尚未确定的任务字段，否则比选表无法对齐。

### 2.4 七张核心数据表

| 表 | 主责 | 阶段 | 主键 | 必填最小集 |
| --- | --- | --- | --- | --- |
| `design_spec.json` | A | P1 | spec_id | product、scope_in、features[]、modules[] |
| `module_map.json` | A | P2 | module_id | feature_refs[]、responsibility、owner_role |
| `dev_task_list.json` | A/E | P6 | task_id | module_id、depends_on[]、estimate_days、owner_role、acceptance[]、priority、source_refs[] |
| `schedule.json` | A | P7 | task_id | wave_no、start_day、end_day、critical、on_path |
| `conflict_register.json` | D | P3/P5 | conflict_id | topic_id、stances[]、level、status |
| `review_sheet.json` | D | P5 | score_id | scores[]、weighted_total、stddev、veto、challenges[] |
| `task_coverage.json` | E | P6 | source_id | rows[]（来源、覆盖任务、状态）、gap_count、coverage_rate |
| `baseline.json` | F | P7 | version | task_ids[]、signed_by、signed_at、source_refs[] |

### 2.5 兼容性硬规则

| 编号 | 规则 | 违反后果 |
| --- | --- | --- |
| C1 | 每张任务卡必须能追溯到 FEA 或 CON，禁止无来源卡 | 覆盖矩阵算不出，`G_P6_P7` 恒为 false |
| C2 | `depends_on` 只能指向存在的 DEV，且不许成环 | `E_DEP_CYCLE`，排期中止并退回 P6 |
| C3 | 每张任务卡至少一条可观测的验收口径 | `G_P6_P7` 不通过，退回 P6 补写 |
| C4 | 三套分解方案的功能点集合与顺序完全一致 | `G_P4_P5` 不通过，P4 原地重跑 |
| C5 | 所有产物带 `meta` 且 `schema_version` 为 1.0 | 编排器拒收 |
| C6 | 模块只返回 `StageResult`，不得自行写 `runs` 或改状态 | 状态与事件流不一致，无法重放 |
| C7 | 加权总分必须是归一化到百分制后的值 | 阈值 80 失去意义 |

### 2.6 模块调用协议

所有模块实现同一签名：接收 `StageContext`，返回 `StageResult`。`StageContext.artifacts` 是只读快照，只含流程配置里声明的输入产物，另含 run_id、stage、budget_left 与 config；`StageResult` 必须含本阶段声明的全部输出产物（各带 meta），另含 events 与 usage。

编排器负责构建上下文、派发、调用、校验、落盘、计费、发事件、求值闸门、转移状态；模块只完成本段语义，不得感知状态机、不得决定下一阶段、不得调用其他模块。

### 2.7 事件契约

事件流只追加不修改，重放依据是 `seq` 单调递增。本次修订在原有事件集里补了任务派发与任务完成两类，因为甘特图与依赖图要按任务粒度取数，只靠阶段事件画不出条。

| 类别 | 事件（共 16 类） |
| --- | --- |
| 生命周期 | `run.start` `run.end` `stage.enter` `stage.exit` |
| 角色 | `agent.on_stage` `agent.statement` `agent.query` `agent.vote` |
| 任务 | `task.dispatched` `task.completed` |
| 冲突 | `conflict.detected` `conflict.resolved` |
| 闸门 | `gate.evaluated` `guard.signal` |
| 资源 | `budget.charged` |
| 人机 | `human.decision` |

实现里另加了两个便于可视化取数的事件：`tasks.decomposed`（P6 任务清单落盘）与 `schedule.computed`（P7 排期算完），不影响上表 16 类的口径。

## 3 阶段规格与流转

P1 为人工输入，P2–P7 为系统执行的六个阶段。每个阶段出口都有闸门，闸门是纯函数，读产物与账本返回布尔值，通过才允许换阶段。

| 阶段 | 名称 | 上场角色 | 主产出 | 出口闸门 |
| --- | --- | --- | --- | --- |
| P1 | 设计规格输入与规范化 | 人 + 编排器 | `design_spec` | `G_P1_P2` |
| P2 | 规格解析与模块划分 | 编排器 + 分类器 | `module_map`、`convocation_table` | `G_P2_P3` |
| P3 | 分解口径讨论与裁决 | A1–A4 | `discussion_minutes`、`conflict_register` | `G_P3_P4`、`G_P3_HUMAN` |
| P4 | 三套分解方案 | C | `breakdown_a/b/c`、`comparison` | `G_P4_P5` |
| P5 | 对抗式评审 | A1 回避，A2–A5 打分 | `review_sheet` | `G_P5_P6`、回炉、`G_P5_HUMAN` |
| P6 | WBS 定稿 | A1 产品经理 + E 校验 | `dev_task_list`、`task_coverage` | `G_P6_P7`、`G_P6_REWORK` |
| P7 | 排期、确认与冻结 | 编排器 + A6 + 人 | `schedule`、`confirmation_sheet`、`baseline`、可视化 | `G_P7_BASELINE`、`G_P7_REWORK` |

各阶段要点：

- **P1**：按字段表抽取，做完整性检查、编号分配、不可判定表述标记。缺字段只走三条路——退回补交、人当场补填、保守标为假设并写明。`G_P1_P2` 判：必填齐、功能点 ≥ 3、模块 ≥ 2。
- **P2**：分类器把功能点与约束分成功能、技术、成本、风险四类；A1 定模块归属与责任角色并生成召集表。留三条后路：一个问题可属两类、低置信度全员召集、架构师与评审员无条件在场。
- **P3**：讨论的不是"做什么"，而是"怎么切"；四个争点固定：拆分粒度、依赖方向、工时依据、验收口径。三段式发言（并行陈述 → 定向质询 → 逐条投票），冲突在质询前登记，不等结束再总结。
- **P4**：三套 WBS 共用同一份功能清单与同一组约束，差别只在切法（按模块细分 / 按里程碑切 / 按风险优先），比选表由代码生成。
- **P5**：质疑必须带齐四要素（问题、影响哪张卡或哪条依赖、严重级、不改会怎样），缺一无效。五维打分 25/25/25/15（覆盖度、可执行性、依赖闭环、验收可测性），成本只估算不计分。加权总分 = 加权原始分 ÷ 权重和（Σw=90），归一化到百分制——早期文档写成"原始分 ÷ 90 × 100"，多乘了一个 100，会让任何方案轻松过线，按前者执行。
- **P6**：A1 依据采纳方案生成任务清单，代码逐条校验八条硬规则（见 4.3），不满足退 P6 补写。优先级与覆盖矩阵都由代码算，不交给模型。
- **P7**：排期不是模型写的，是代码算的（见 5.2）；A6 出确认单，人只能签字、打回、批注；签字后基线冻结 v1.0，可视化页面同时导出。

### 3.1 两套"任务"必须分清

本方案的"任务分解"指两个不同对象，这是评审最容易被追问的一点：

- **编排器的执行卡**：例如"派 A2 做功能粒度立场陈述"，是引擎内部派活单位（4.1 的 24 张卡）；
- **系统交付的开发任务清单**：例如"DEV-004 商品详情接口联调"，是产品产物（4.3 的 `dev_task_list`）。

前者是手段，后者是目的。评审时若把内部执行卡当成交付物，就会被追问"我做微信的登录任务在哪里"。

## 4 任务分解

### 4.1 编排器的执行卡（24 张）

其中 8 张是纯代码卡、不耗模型预算；16 张需要调用模型，五维打分按四个角色各一次计，合计 19 次调用，全局上限 30 次，余 11 次留给质询扩对、格式重试与回炉。

| 阶段 | 卡号 | 主要任务 | 调用 |
| --- | --- | --- | --- |
| P1 | T-P1-01 | 设计规格规范化与校验 | 0 |
| P2 | T-P2-01 / T-P2-02 | 四类分类 / 模块归属与召集 | 1 / 0 |
| P3 | T-P3-01…08 | 四份立场陈述、冲突扫描、定向质询、逐条投票、三级裁决 | 4 + 1 + 1 次，另 2 张代码卡 |
| P4 | T-P4-01…05 | 功能清单冻结、三套 WBS、比选表 | 4 次，比选表 0 |
| P5 | T-P5-01…04 | 支持陈述、反方质疑、五维打分、门禁分流 | 1 + 1 + 4 次，门禁 0 |
| P6 | T-P6-01 / T-P6-02 | WBS 生成 / 卡校验与覆盖矩阵 | 1 / 0 |
| P7 | T-P7-01 / T-P7-02 | 确认单与意见处理 / 排期、冻结与导出 | 1 / 0 |

### 4.2 依赖图的五条结构约束

1. P3 的四张立场卡同层无连边：四人同时写、互相看不到，防止第一个开口的人框住讨论。
2. 冲突扫描是唯一全同步点：必须等四份都写完才能扫全，扫不全就漏冲突。
3. P4 三条边从同一张功能清单卡出发：三套方案共用同一份清单，后面才可能逐行比选。
4. P5 的支持陈述与反方质疑之间没有边：两者互不参考，避免评审变成互相递话。
5. P6 到 P7 严格串行：没有定稿的任务清单，排期无从谈起。

### 4.3 开发任务清单的八项字段与硬规则

| 字段 | 含义 | 校验 |
| --- | --- | --- |
| `task_id` | DEV-001 | 唯一，不许重复 |
| `module_id` / `module` | 所属模块 MOD-* | 必须能追到功能点或约束 |
| `title` | 一卡一件事 | 粒度 0.5–3 人天，超 3 人天必须再拆 |
| `depends_on[]` | 依赖的任务号 | 只能指向存在的 DEV，不许成环，不许双向 |
| `estimate_days` | 工时（人天） | 正数 |
| `owner_role` | 负责人（唯一） | 不允许"多人共同负责" |
| `acceptance[]` | 验收口径 | 至少一条可观测：什么操作之后看到什么结果 |
| `feature_refs[]` / `source_refs[]` | 来源引用（FEA/CON） | 无来源的卡不许进清单 |

另有两条：不许写"联调""优化""杂项"这类不可验收的卡，联调要拆成具体的接口对；切分顺序是先按模块边界、再按依赖分层、最后按人天切细，同一模块内同一文件不允许跨波并行。

## 5 编排策略

### 5.1 路由表（12 行）

| 闸门 | 转移 | 判定条件 | 不满足时 |
| --- | --- | --- | --- |
| `G_P1_P2` | P1→P2 | 必填字段齐、功能点 ≥ 3、模块 ≥ 2 | 留在 P1 |
| `G_P2_P3` | P2→P3 | 每功能点有类型、置信度、责任角色；低置信度已全员召集 | 留在 P2 |
| `G_P3_P4` | P3→P4 | 未决冲突为零，或已满三轮 | 继续 P3，轮次加一 |
| `G_P3_HUMAN` | P3→等待人 | 存在升级级冲突且状态为已升级 | — |
| `G_P4_P5` | P4→P5 | 三套功能点集合相同且非空，比选表覆盖全部功能点 | 留在 P4 重跑 |
| `G_P5_P6` | P5→P6 | 总分 ≥ 80、无否决项、标准差 < 12 | 按原因分级回炉 |
| `G_P5_REWORK` | P5→P4 或 P3 | 未通过：方案层退 P4，需求层退 P3 | — |
| `G_P5_HUMAN` | P5→等待人 | 修改累计达三次 | — |
| `G_P6_P7` | P6→P7 | 覆盖空缺为零、每卡有验收、任务图无环无缺字段、每个功能点有任务承接 | 退回 P6 补卡 |
| `G_P6_REWORK` | P6→P3 或 P6 | 有来源未被任何任务覆盖 | — |
| `G_P7_BASELINE` | P7→冻结 | 已签字且产物齐、覆盖通过 | 留在 P7 等人 |
| `G_P7_REWORK` | P7→P3 | 已打回且次数未超限 | 第三次转升级态 |

判定优先级固定为：终止类 > 人工类 > 回炉类 > 前进类 > 停留。例：P5 同时满足"总分过线"与"预算耗尽"时，先判预算耗尽转等待人，因为继续走只会多耗预算而不改变结论。闸门不使用动态求值语法，`gate_rule.yaml` 只写函数名与参数，函数在 `gate_check` 里注册为纯函数。

### 5.2 排期算法（五步）

1. **校验**：任务号唯一、依赖目标存在、负责人合法、工时为正。
2. **查环**：Kahn 拓扑排序，排不完的节点即环，报 `E_DEP_CYCLE` 并列出环上任务。
3. **分层定波**：同层无依赖的任务进同一波，波内并行；并行度超上限的任务按优先级顺延到下一波并记录原因。
4. **关键路径**：以工时加权求最长路径，它是总工期的下界，路径上的任务不允许为了"看起来均衡"而挪动。
5. **资源冲突**：同一负责人在同一波被排两张以上即冲突，按 M > S > C 保留高优先级，其余延后一波并写进 `conflicts` 字段。

输出 `schedule.json` 给三组数：波次表（每波的任务、起止日、并行数）、关键路径（任务序列与总工时）、总工期与并行度曲线。这三组数是"编排"与"清单"的分界线，也是答辩最能说明差异的地方。

### 5.3 调度主循环

两个刻意的顺序：**闸门在派活之前判**（先问"这个阶段能不能结束"），**预算在整轮末尾判**（中途打断会留下半张卡的结果，重放对不上）。

```
FUNCTION step(runtime, state):
    verdict = evaluate(state, artifacts, ledger, gates)      # 先判闸门
    IF verdict.action IN (advance, rework, freeze, wait_human, escalate):
        apply_transition(state, verdict); RETURN
    ready = [card FOR card IN cards IF all_done(card.depends_on)]
    IF ready IS EMPTY: escalate(state, "deadlock"); RETURN
    FOR card IN ready[:concurrency]:
        result = MODULES[card.owner].run(pack_context(card, state))
        validate(result); store_artifacts(result); charge(result); emit(result.events)
    IF ledger.global_used >= limit: escalate(state, "budget_exhausted")
```

### 5.4 预算与终止阈值

只有模型调用计费，一次调用记一次；闸门、冲突扫描、优先级、覆盖矩阵、打分统计、排期全是纯代码，不计费——这是把"零成本把关"放在代码里的原因。

| 项目 | 阈值 | 超限动作 |
| --- | --- | --- |
| 全局模型调用 | 30 | 转等待人，输出未收敛报告 |
| 单阶段调用 | P2 4 / P3 12 / P4 6 / P5 8 / P6 4 / P7 2 | 该阶段停止，交闸门判 |
| P3 轮次 | 3 | 满足 `G_P3_P4`，即使仍有未决冲突 |
| P5 修改 | 3 | 转等待人 |
| P7 打回 | 2 | 第三次转升级态 |
| 并行度 | 见附录B（实现默认 4） | 超出任务按优先级顺延一波 |
| 单卡工时 | 3 人天 | 必须再拆，否则 `G_P6_P7` 不通过 |

口径说明：单阶段上限管"这个阶段还能不能再跑"，全局上限才是整轮终止条件。早期实现把两者混在一条判定里，出现"P7 第二次进来只是签字后重算冻结却被判预算耗尽"的误伤，现已分开处理。

### 5.5 异常判定与处理

| 异常 | 判定 | 处理 |
| --- | --- | --- |
| 产物缺失 | 上下文缺声明项 | `E_ARTIFACT_MISSING`，不转移状态，退回上游补 |
| 格式不符 | 缺字段、枚举越界、引用不通 | `E_SCHEMA_INVALID`，允许 1 次重试，仍失败该卡作废 |
| 依赖成环 | 拓扑排序排不完 | `E_DEP_CYCLE`，退回 P6 拆卡并记录环 |
| 超时 | 单卡超 120 秒 | `E_AGENT_UNAVAILABLE`，不扣预算，记事件 |
| 死锁 | 就绪队列空且无可推进项 | 转升级态，附卡住的卡清单 |
| 发言趋同 | 语义相似度 ≥ 0.85 或字面 0.70 | 判无效重说；同议题补 2 次仍趋同则挂起换角度 |
| 答非所问 | 质询回答未针对被引发言 | `E_EVASIVE`，强制重答 1 次 |
| 预算耗尽 | 全局调用达 30 | 转等待人，输出未收敛报告 |

### 5.6 人类介入与三级裁决

三个必须停的位置：补全设计规格（P1）、裁决挂起项（等待人）、签字（P7）。其余任意点人可主动暂停，但系统不主动等人，否则整套流程退化成审批流。权限上，提规格的人可暂停、批注、改派、中止，但不能签字；签字人可做全部动作。提需求与确认需求不应是同一双手，否则"确认"失去意义。

冲突按证据强弱三级收敛：

1. **L1 证据优先**，不投票：一方有证据引用、另一方只有主张，直接采有证据的一方。
2. **L2 加权投票**：双方都有依据时按角色权重算票，用户代表与质量评审员各 1.5，产品经理与架构师各 1.0，差值绝对值达 1.0 即判定。
3. **L3 挂起**：仍分不出，标升级级转人工裁决。

给前两者更高权重，是因为它们的诉求被牺牲后返工代价最大——用户代表失效导致验收失败，质量评审员失效导致上线出事。

### 5.7 打回与基线变更

打回携带原因、已有方案与已有意见回到 P3，原因作为新约束广播，后续每个角色回应时必须先回应它；同一份设计规格最多打回两次。基线冻结后的改动不进主状态机，而是开一次独立子运行：新运行继承 v1.0 的追溯链，原基线不可物理修改，v1.1 只能新增；任务覆盖矩阵必须重算通过才允许冻结——老矩阵只覆盖老规格，沿用不报错但会漏。

## 6 可视化与交互

### 6.1 一条原则：界面是事件的投影

渲染函数输入只有事件数组与截止序号，输出界面，本身是纯函数。"实时"取截止序号即最新，"回放"由进度条给，同一套代码同时拿到监控与复盘。界面不持有任何业务状态，否则会出现两套真相。依赖图与甘特图同理：只读 `schedule.json` 与任务事件，不自己重算依赖。

### 6.2 七个视图

| 视图 | 回答什么 | 主区域 |
| --- | --- | --- |
| V1 运行时间轴 | 现在跑到哪、谁在说话 | 横轴事件序号，泳道为编排器与 A1–A6 |
| V2 讨论看板 | 三段各自进行到哪 | 并行陈述、定向质询、投票三栏 |
| V3 冲突矩阵 | 哪些议题未裁决、谁与谁不一致 | 行是议题、列是角色、格是立场与证据标记 |
| V4 闸门灯与预算条 | 能不能过、还剩几次调用 | 顶部固定横条 |
| V5 任务依赖图与甘特 | 谁先谁后、哪些并行、哪条链最紧 | 左依赖图、右甘特，关键路径高亮 |
| V6 覆盖热图 | 哪条规格要求没被任务覆盖 | 行是规格来源、列是非 Wont 任务，空缺留白 |
| V7 回放控制 | 那一刻到底发生了什么 | 底部进度条、单步、跳到下一异常 |

V5 是本次修订新增的硬要求：依赖图解决"看得懂结构"，甘特解决"看得懂时间"。只画甘特看不出为什么两张卡不能并行，只画依赖图感受不到工期压力，两者必须同屏；坐标按波次分层，条长按工时，关键路径加粗描边，并行度超上限的波次标注"顺延 N 张卡"。

三处细节：有证据必须可见（V3 格子右上角点小圆点）；空缺用留白表达而非涂满红色（满屏红会被无视）；异常必须可见（发言趋同的块叠灰蒙层并标相似度数值）。

### 6.3 交互动作与门禁

| 动作 | 前置门禁 | 生效时机 | 事件字段 |
| --- | --- | --- | --- |
| 暂停 | 运行中 | 当前卡结束后软停 | `action=pause`、reason |
| 恢复 | 已暂停 | 立即 | `action=resume`、from_seq |
| 批注 | 任意 | 下一调度步 | `action=comment`、scope、text |
| 打回 | P7 确认态 | 立即 | `action=reject`、reason（必填） |
| 签署 | P7 且闸门全过 | 立即 | `action=sign`、signed_by |
| 裁决挂起 | 等待人且存在升级级冲突 | 立即 | `action=adjudicate`、scope.conflict_id |
| 中止 | 任意 | 当前卡结束后 | `action=abort` |

底线：所有人工操作先落成 `human.decision` 事件再进编排器，不允许界面直接改状态——可追溯、可重放、可追责。裁决必须带冲突号，批注必须定位到具体任务或冲突，不给作用域的不许注入，否则等于开了"随时改需求"的后门。

### 6.4 落地方式

命令行优先落地，图形界面与命令行共用同一套渲染输入。渲染函数输入 `events.jsonl` 与 `schedule.json`，输出自包含 `index.html`（SVG 绘制、不依赖外部资源、断网可看）。命令行入口为 `viz` 子命令，回放通过进度参数控制截止序号。
