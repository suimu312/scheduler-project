# 角色管理与三段式讨论

> 负责人：韩晓萱（B · 角色与讨论管理）｜对应阶段：P2 问题识别召集 + P3 三段式发言（并行陈述 / 定向质询 / 结构化投票）
>

---

## 1. 本模块管什么

**一句话**：让 6 个 Agent 各带各的脑子上场，把问题聊透、把分歧逼出来，而不是异口同声说正确的废话。

| | 内容 |
|---|---|
| 输入 | 原始需求材料；角色提示词模板与议题词表（本模块维护）；知识边界切片配置（本模块维护） |
| 输出 | 角色卡 `RoleCard` ×6、议题 `Issue`、立场陈述 `Stance`、问答对 `QA`、投票记录 `Vote`、相似度报告 `SimilarityReport`；对外文档 `docs/agent-roles.md` |
| 下游 | C 拿结构化讨论结果做方案；D 引用议题词表并接收立场陈述与问答对 |
| 不负责 | 不写方案（C 的活）、不做裁决（D 的活）、不做流程调度（A 的活） |

**边界要说清的一点**：本模块只管"谁上场、能看到什么、必须怎么说、不许怎么说"，不管"说的对不对"。观点成立与否交给 D 按证据裁决。这样切，是为了让"讨论充分性"和"结论正确性"各有唯一的责任人。

**编号约定**：6 个 Agent = 编排器 `A0`（即模块 A 的执行体）+ `A1`–`A5`，A1–A5 的角色含义与 D 模块完全一致。

### 1.1 P2/P3 的几步怎么走

| 阶段 | 步 | 谁 | 做什么 | 产出 |
|---|---|---|---|---|
| P2 | ① 材料分发 | A0 | 按知识切片把原始材料分发给各角色 | 分发记录 |
| P2 | ② 问题识别 | A1–A5 | 各自按角色视角提问题 | 原始问题清单 |
| P2 | ③ 议题归并 | A0 执行、B 规则 | 按议题词表归一去重，登记 `Issue` | 议题列表 |
| P3 | ④ 并行陈述 | A1–A5 | 同时独立提交立场，互不可见 | `Stance` |
| P3 | ⑤ 定向质询 | A1–A5 | 只针对分歧立场问答，轮次封顶 | `QA` |
| P3 | ⑥ 结构化投票 | A1–A5 | 固定票型、强制理由投票 | `Vote` |

**A0 全程不持立场、不投票**：它的职责是控场，一旦它表态，就没有人能裁判流程是否公正。这条和真实会议里主持人不参与表决是同一件事。

## 2. 数据结构

### 2.1 RoleCard（角色卡）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | `A0`–`A5` |
| `name` | enum | 是 | 编排器 / 产品经理 / 用户代表 / 架构师 / 质量评审员 / 需求分析师 |
| `version` | string | 是 | 模板版本，语义化版本号，变更必须留痕 |
| `prompt_keypoints` | list | 是 | 提示词要点，按固定四段式组织（见 3.1） |
| `stance_constraint` | object | 是 | `{must_defend, must_challenge}`，义务性立场 |
| `knowledge_scope` | ref | 是 | 绑定的知识切片 ID（见 2.2） |
| `entry_rule` | object | 是 | `{stages, exit_condition}`，上场与退场规则 |
| `ballot_quota` | int | 是 | 投票配额，A0 = 0，其余 = 1 |

**六张角色卡总表**：

| Agent | 角色 | must_defend（必须维护） | must_challenge（必须质疑） | 独占切片 | 禁见切片 |
|---|---|---|---|---|---|
| A0 | 编排器 | 流程中立与规则执行 | 任何破坏规则的发言行为 | 全部材料（仅用于控场，禁止引用表态） | — |
| A1 | 产品经理 | 需求价值、交付节奏与成本约束 | 价值不清、投入产出比不明的需求 | 业务目标、预算与排期 | 技术实现细节 |
| A2 | 用户代表 | 核心场景走通与使用体验 | 绕过真实场景的臆想需求 | 用户画像、真实场景与反馈 | 预算与排期数字 |
| A3 | 架构师 | 技术可行性与系统稳定性 | 无法落地、代价失控的设想 | 现有架构、技术选型、运维数据 | 预算数字 |
| A4 | 质量评审员 | 安全、合规与风险底线 | 带故障隐患和合规缺口的设计 | 历史故障库、合规清单、安全基线 | 商业优先级排序 |
| A5 | 需求分析师 | 需求无歧义、可验证 | 模糊表述、无法验收的条目 | 验收标准库、术语表 | 方案草稿 |

**为什么每个角色都要有 `must_challenge`**：大模型的默认姿态是"配合"，不强制它承担质疑义务，整场讨论就会变成互相点头。把"必须挑什么刺"写进角色卡，等于给每个角色发一份规定动作，从结构上保证至少有反对声存在。

### 2.2 KnowledgeSlice（知识边界切片）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `slice_id` | string | 是 | `K-013` |
| `owner` | ref | 是 | 绑定的 Agent |
| `exclusive` | list | 是 | 独占材料，其他角色默认不可见 |
| `visible` | list | 是 | 可见材料清单 |
| `forbidden` | list | 是 | 禁见材料，引用其中内容的发言直接判无效 |

**为什么要切知识边界**：同一个底层模型，喂同样的材料，再怎么叮嘱"请独立思考"，产出也会趋同。真实评审会里，用户本来就不懂架构细节，架构师也不掌握预算——**信息差才是异质性的来源**，光靠提示词里写性格差异是撑不住的。

### 2.3 Issue 与 TopicVocabulary（议题与议题词表）

`Issue`：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `issue_id` | string | 是 | `I-007` |
| `topic_id` | ref | 是 | 必须命中议题词表，**不许自造** |
| `raised_by` | ref | 是 | 首个提出的 Agent |
| `description` | string | 是 | 问题表述 |
| `status` | enum | 是 | `OPEN` / `IN_DISCUSSION` / `CLOSED` |

`TopicVocabulary`：`{topic_id, aliases, owner: B, version}`。

**词表由 B 维护、D 只引用**：这条与 D 模块的 `Conflict.topic_id` 规则对齐。否则"手机号能不能给看"和"隐私保护"会被登记成两个议题，D 那边的冲突永远对不上。新议题必须先入词表再讨论，顺序不能反过来。

### 2.4 Stance（立场陈述）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | `S-013` |
| `issue_id` | ref | 是 | 针对的议题 |
| `agent` | ref | 是 | 陈述者 |
| `position` | enum | 是 | `FOR` / `AGAINST` / `NEUTRAL` |
| `claim` | string | 是 | 核心主张 |
| `evidence_ref` | list | 是 | 证据必须来自本角色 `visible` 范围，引用禁见材料判无效 |
| `round` | int | 是 | 轮次，补发言时递增 |

**并行陈述互不可见**：所有角色同时提交，提交解封前看不到任何他人内容。先发言的人会锚定后发言的人，这是讨论中最常见的趋同来源，物理隔离比提示词里写一百遍"不要受他人影响"都管用。

### 2.5 QA（定向质询问答对）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | `Q-013` |
| `issue_id` | ref | 是 | 所属议题 |
| `from` / `to` | ref | 是 | 质询方与被质询方，必须指向具体角色 |
| `question` | string | 是 | 必须针对某条 `Stance`，不许泛泛提问 |
| `answer` | string | 是 | 被质询方必须正面回答 |
| `round` | int | 是 | 质询轮次，上限 2 |

### 2.6 Vote（结构化投票）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | `V-013` |
| `issue_id` | ref | 是 | 投票议题 |
| `agent` | ref | 是 | 投票人，一人一票 |
| `ballot` | enum | 是 | `FOR` / `AGAINST` / `ABSTAIN` |
| `reason` | string | 是 | **无理由票作废**，弃权同样要写理由 |

**P3 投票一人一票，不做加权**：加权裁决是 D 模块二级裁决的口径（A2、A4 权重 1.5），B 不越权定义。本模块只如实记录票型，分歧压不压得住由 D 决定——两个模块各算各的，口径才不会打架。

### 2.7 SimilarityReport（相似度报告）

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | `M-013` |
| `round` | int | 是 | 所属陈述轮次 |
| `pair` | list | 是 | 受检的两个 Agent |
| `semantic_score` | float | 是 | 语义相似度（embedding 余弦，0–1） |
| `lexical_score` | float | 是 | 字面相似度（n-gram 重合度，0–1） |
| `flagged` | bool | 是 | 是否判定趋同 |
| `action` | enum | 是 | `PASS` / `RETRY` |

## 3. 规则表

### 3.1 提示词模板管理

| 规则 | 说明 |
|---|---|
| 固定四段式 | 每张角色卡必须包含：角色目标 / 立场约束 / 知识边界 / 上场规则，缺段拒绝加载 |
| 版本化管理 | `version` 变更留痕；运行中的流程禁止热替换模板，只能沿用当前版本 |
| 静态扫描 | 模板中出现"参考其他角色观点""与大家保持一致"等引导趋同的措辞，加载时直接拦截 |
| 文档对齐 | 模板的每个版本必须与 `docs/agent-roles.md` 同版本，配置改、文档同步改 |

### 3.2 异质性配置

| 条件 | 动作 |
|---|---|
| 非 A0 角色没有独占切片或没有禁见切片 | 配置校验失败，禁止开会 |
| `must_challenge` 为空 | 配置校验失败，角色卡退回补写 |
| 同一材料同时出现在 `visible` 和 `forbidden` | 配置冲突，禁止开会，由 B 修正 |
| 两个角色的 `visible` 完全相同 | 告警，要求至少保留一个差异切片 |

### 3.3 防趋同：相似度检测与强制补发言

```
# 阈值写死：语义 >= 0.85 或 字面 >= 0.70 即判趋同
for each round of Stance:
    for pair in combinations(agents, 2):
        semantic = cosine(embedding(a), embedding(b))
        lexical  = ngram_overlap(a, b)
        flagged  = (semantic >= 0.85) or (lexical >= 0.70)

    if any flagged pair:
        保留先提交者，后提交者强制补发言   # 后提交者才有条件抄别人
```

**补发言的三条硬要求**：

1. 必须引用本角色独占切片中的证据至少 1 条；
2. 新文本与原文本语义相似度必须 < 0.6，不许换个说法重复同一观点；
3. 同一议题最多补 2 次，第 3 次仍判趋同 → 记 `E_GROUPTHINK`，议题挂起并由 A0 更换提问角度后重开。

**两个口径必须写死，否则实现时一定出错**：

- **双口径取"或"不取"与"**。模型换几个同义词就能绕开字面检测，但语义分照样暴露；只看语义又会漏掉大段复制粘贴。任一命中即标记，没有空子可钻。
- **相似度由代码计算，不许模型自评**。让模型判断自己和别人像不像，它永远觉得自己很独立，这条和 D 模块"驳回率不许模型自评"是同一个道理。

### 3.4 P2 问题识别召集

| 规则 | 说明 |
|---|---|
| 召集触发 | 原始材料进入即由 A0 按本模块规则发起，无人工前置条件 |
| 数量约束 | 每个角色至少提 2 个问题，至多 5 个，超出的按角色相关度裁剪 |
| 议题归并 | 按词表 `aliases` 归一，重复问题合并，保留最早提出者 |
| 词表更新 | 未登记的新话题先入词表、拿到 `topic_id` 后才允许讨论 |

### 3.5 P3 三段式发言

**第一段·并行陈述**

| 规则 | 说明 |
|---|---|
| 同时发起 | A0 同一时刻向所有角色发起，统一截止时间 |
| 互不可见 | 截止提交前，任何角色看不到他人内容 |
| 超时处理 | 逾期未交按缺席处理并记事件，不等齐也不拖堂 |

**第二段·定向质询**

| 规则 | 说明 |
|---|---|
| 准入条件 | 只允许针对同一议题下立场对立的 `Stance` 发起 |
| 轮次封顶 | 每个议题最多 2 轮问答，防止无限拉扯 |
| 正面回答 | 答非所问、回避不答记 `E_EVASIVE`，强制重答 1 次 |
| 回炉复用 | D 模块退回到 B 的"重开定点质询"，走完全相同的流程，不另开口径 |

**第三段·结构化投票**

| 规则 | 说明 |
|---|---|
| 一人一票 | A0 不投，A1–A5 各 1 票，票型枚举固定 |
| 理由强制 | 无理由的赞成/反对票、无理由的弃权一律作废，补投 1 次 |
| 平票处理 | 一次平票 → 回到定向质询再投一轮；二次平票 → 标 `CONTROVERSIAL` 移交 D，B 不自行裁定 |
| 有效票门槛 | 有效票不足 3 张时不强行出结论，议题挂起 |

### 3.6 上场规则总表

| Agent | P2 | P3 | P5 |
|---|---|---|---|
| A0 编排器 | 召集、控场 | 控场，不陈述不投票 | 不参与 |
| A1 产品经理 | 在场 | 陈述 / 质询 / 投票 | **回避退场**（作者不评自己的方案，与 D 对齐） |
| A2 用户代表 | 在场，主召集 | 全程 | 打功能完整性分 |
| A3 架构师 | 在场 | 全程 | 打技术可行性分 |
| A4 质量评审员 | 在场 | 全程 | 反方质疑 + 打风险安全分 |
| A5 需求分析师 | 在场 | 全程 | 打可测试性分 |

**送 D 的立场陈述为什么是四份**：P3 阶段 A1–A5 共五份陈述，但 A1 在 P5 回避，向 D 输出时按回避规则剔除 A1，故 D 收到的是 A2–A5 四份立场陈述与问答对——两边数字对得上，不是漏发。

## 4. 失败处理

| 情况 | 处理 |
|---|---|
| 角色卡缺段、版本号非法 | 记 `E_ROLE_INVALID`，阻断启动，允许修复 1 次 |
| 知识切片 `visible` 与 `forbidden` 冲突 | 配置校验失败，禁止开会，B 修正后重新校验 |
| 发言引用禁见材料 | 该条作废，要求重写 1 次，再犯按缺席处理 |
| 模型返回格式不符（枚举越界、缺字段） | 允许 1 次重试，仍失败按缺席记事件，不阻塞其他角色 |
| 相似度检测服务不可用 | 降级为字面单口径并在报告中标注降级，**不得跳过检测**直接进入下一段 |
| 被质询方回避或答非所问 | 记 `E_EVASIVE`，强制重答 1 次 |
| 无理由投票或无理由弃权 | 票作废，补投 1 次 |
| 单 Agent 全程零发言 | 触发强制补发言；仍无发言按缺席，有效票不足 3 张则议题挂起 |
| 补发言 2 次后仍趋同 | 记 `E_GROUPTHINK`，议题挂起，A0 换角度重开 |
| 两轮投票仍平票 | 标 `CONTROVERSIAL` 移交 D，不允许 B 内部强行拍板 |
| B/D 两侧议题词表不一致 | 以 B 词表为唯一源阻断同步，不一致期间 D 不得登记新冲突 |
| 全员票型一致且均无实质理由 | 判异常（疑似未实际讨论），整段打回并行陈述 |

## 5. 与其他模块的接口

| 对象 | 约定 |
|---|---|
| A（编排器） | B 只提供规则、模板与配置，不自行执行；P2/P3 动作全部由 A0 按 B 规则触发，通过 `ISSUE_RAISED` / `STANCE_READY` / `QA_DONE` / `VOTE_DONE` / `GROUPTHINK_FLAGGED` 事件上报 |
| C（方案） | 只接收 `Stance`、`QA`、`Vote` 的结构化结果，不读取原始过程发言，避免被过程噪音带偏 |
| D（评审） | 议题词表由 B 维护、D 引用；D 的 `Conflict.topic_id` 必须命中 B 词表；回炉到 B 时复用定向质询流程；送 D 的陈述按 A1 回避规则输出四份 |
| E（需求） | 收敛议题与投票结论作为需求条目的"讨论来源链"，可追溯到该议题在 P3 的全部发言与票型 |
| `docs/agent-roles.md` | B 对外交付的角色设计文档，内容为每个 Agent 的 prompt 要点、立场约束、上场规则，与 `RoleCard` 同版本；配置任何变更，文档同步更新 |
